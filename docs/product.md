# ServerPilot

## Назначение документа

Этот документ описывает конечную идею ServerPilot, целевую архитектуру и направления развития проекта.

Границы ближайшей реализации определяются файлом `docs/mvp.md`.

При противоречии между этим документом и `docs/mvp.md` приоритет имеет `docs/mvp.md`.

Технологии и функции из этого документа не должны автоматически добавляться в текущую реализацию. Они внедряются поэтапно, когда базовый сценарий уже работает и появляется практическая причина для их использования.

## Краткое описание

ServerPilot — система удалённого управления локальными игровыми и прикладными серверами.

На Windows-компьютере пользователя устанавливается Agent, который работает как фоновая служба и управляет локальными серверными процессами.

Через веб-интерфейс пользователь сможет:

- запускать серверы;
- останавливать серверы;
- перезапускать серверы;
- отслеживать их состояние;
- просматривать логи;
- просматривать нагрузку CPU и RAM;
- создавать резервные копии;
- восстанавливать резервные копии;
- настраивать автоматические действия;
- просматривать историю операций.

Первоначально система будет ориентирована на сервер Project Zomboid.

Архитектура должна позволять в дальнейшем управлять другими приложениями, запускаемыми через `.exe`, `.bat` или другой локальный исполняемый файл.

## Основной пользовательский сценарий

Пользователь устанавливает ServerPilot Agent на Windows-компьютер, где находится игровой или прикладной сервер.

Agent регистрируется в ServerPilot и сообщает backend, что он доступен.

Пользователь открывает веб-интерфейс и добавляет сервер, указывая:

- название;
- тип сервера;
- путь к исполняемому файлу или `.bat`;
- аргументы запуска;
- рабочую директорию;
- имя процесса;
- директорию с логами;
- директорию с файлами сервера;
- директорию для резервных копий.

После этого пользователь может управлять сервером через сайт.

Пример запуска:

1. Пользователь нажимает «Запустить».
2. React отправляет запрос в ASP.NET Core API.
3. Backend создаёт команду `StartServer`.
4. Команда сохраняется и передаётся Agent.
5. Windows Agent получает команду.
6. Agent проверяет текущее состояние процесса.
7. Agent запускает локальный сервер.
8. Agent сообщает backend результат выполнения.
9. Backend обновляет состояние команды и сервера.
10. Веб-интерфейс показывает актуальный статус.

В текущем MVP передача команд выполняется через HTTP polling.

RabbitMQ должен быть добавлен позже, когда базовый сценарий уже работает и можно осознанно заменить или расширить механизм доставки сообщений.

## Целевая архитектура

Система состоит из нескольких компонентов.

### Web Client

Frontend на React и TypeScript.

Основные функции:

- регистрация и авторизация;
- список подключённых агентов;
- список серверов;
- добавление и настройка сервера;
- запуск;
- остановка;
- перезапуск;
- отображение текущего состояния;
- отображение CPU и RAM;
- просмотр логов;
- создание резервных копий;
- восстановление резервных копий;
- история выполненных команд;
- настройка расписаний;
- просмотр ошибок.

Web Client не входит в самый ранний этап MVP.

Первые сценарии могут проверяться через HTTP-клиент.

### ASP.NET Core API

Основной backend системы.

Отвечает за:

- пользователей;
- авторизацию;
- регистрацию Windows Agent;
- аутентификацию Agent;
- хранение конфигурации серверов;
- создание команд;
- выдачу команд агентам;
- получение результатов выполнения;
- хранение истории;
- проверку прав доступа;
- управление резервными копиями;
- управление расписаниями;
- предоставление данных frontend;
- публикацию сообщений в RabbitMQ на последующих этапах.

Backend не запускает серверные процессы напрямую, поскольку они находятся на удалённых Windows-компьютерах.

### Windows Agent

Отдельное приложение на C#.

На раннем этапе Agent запускается как обычное консольное приложение на базе .NET Worker Service.

В дальнейшем Agent должен устанавливаться и работать как Windows Service.

Agent имеет доступ к локальным процессам и файлам.

Основные функции:

- регистрация в backend;
- отдельная аутентификация Agent;
- периодическая отправка heartbeat;
- получение команд;
- запуск процессов;
- корректная остановка процессов;
- принудительное завершение зависших процессов;
- перезапуск;
- отслеживание PID;
- проверка фактического состояния процесса;
- получение CPU и RAM;
- чтение логов;
- создание резервных копий;
- восстановление резервных копий;
- отправка результатов выполнения;
- обнаружение аварийного завершения;
- повторное подключение при временной недоступности backend.

Agent не должен выполнять произвольный код, полученный от backend.

Он должен поддерживать ограниченный набор строго типизированных команд.

Путь к исполняемому файлу, аргументы и рабочая директория должны браться из заранее сохранённой конфигурации `ServerInstance`, а не передаваться как произвольная команда при каждом запуске.

### Worker Service

Отдельный фоновый серверный сервис.

Предполагаемые задачи:

- обработка расписаний;
- создание автоматических команд;
- очистка старых резервных копий;
- проверка недоступных агентов;
- обработка повторных попыток;
- отправка уведомлений;
- периодические системные задачи;
- определение устаревших команд;
- обработка таймаутов.

Worker не обязателен для первого вертикального сценария.

Он должен добавляться только после появления фоновых задач, которые действительно требуют отдельного процесса.

### PostgreSQL

Основная база данных и источник истины.

Предполагаемые сущности:

- `User`;
- `Agent`;
- `AgentInstallationToken`;
- `ServerInstance`;
- `ServerCommand`;
- `ServerEvent`;
- `ServerMetric`;
- `Backup`;
- `Schedule`;
- `ConfigurationVersion`.

PostgreSQL используется с самого раннего этапа проекта.

### RabbitMQ

RabbitMQ планируется использовать для асинхронной передачи команд и событий.

Он не входит в текущий MVP.

Сначала взаимодействие API и Agent реализуется через HTTP polling. После появления рабочего сценария RabbitMQ может быть добавлен для изучения брокеров сообщений, повторной доставки, маршрутизации и обработки событий.

Примеры команд:

- `StartServer`;
- `StopServer`;
- `RestartServer`;
- `CreateBackup`;
- `RestoreBackup`;
- `CollectStatus`;
- `UpdateConfiguration`.

Примеры событий:

- `ServerStarted`;
- `ServerStopped`;
- `ServerCrashed`;
- `CommandCompleted`;
- `CommandFailed`;
- `BackupCreated`;
- `BackupFailed`;
- `AgentConnected`;
- `AgentDisconnected`.

Сообщения должны содержать:

- идентификатор сообщения;
- идентификатор команды;
- идентификатор Agent;
- идентификатор ServerInstance;
- тип сообщения;
- время создания;
- номер попытки;
- correlation ID;
- trace ID при наличии;
- версию контракта.

Необходимо предусмотреть:

- идемпотентность;
- повторные попытки;
- dead-letter queue;
- защиту от повторной обработки;
- обработку таймаутов;
- наблюдаемость;
- версионирование контрактов.

### Redis

Redis может использоваться для:

- кеширования текущего состояния серверов;
- хранения последнего heartbeat;
- кеширования последних метрик;
- распределённых блокировок;
- защиты от одновременного выполнения конфликтующих команд;
- временных данных;
- rate limiting.

Redis не обязателен для MVP.

Он должен добавляться только после появления конкретной задачи, которую неудобно или неэффективно решать через PostgreSQL.

### Хранилище резервных копий

На первом этапе резервные копии могут храниться локально на компьютере с Agent.

Позже можно добавить MinIO или другое S3-совместимое хранилище.

Backend хранит метаданные резервной копии:

- идентификатор;
- сервер;
- дата создания;
- размер;
- локальный путь или object key;
- статус;
- причина создания;
- контрольная сумма;
- время завершения;
- информация об ошибке.

## Основные сущности

### User

Представляет пользователя системы.

Основные поля:

- `Id`;
- `Email`;
- `PasswordHash`;
- `CreatedAt`.

На раннем этапе достаточно одного типа пользователя без сложной ролевой модели.

### AgentInstallationToken

Одноразовый токен для первичной регистрации Agent.

Основные поля:

- `Id`;
- `UserId`;
- `TokenHash`;
- `ExpiresAt`;
- `UsedAt`;
- `RevokedAt`;
- `CreatedAt`.

Исходное значение токена не должно храниться в базе данных.

### Agent

Представляет Windows-компьютер, на котором установлен ServerPilot Agent.

Основные поля:

- `Id`;
- `UserId`;
- `Name`;
- `MachineName`;
- `OperatingSystem`;
- `AgentVersion`;
- `Status`;
- `LastSeenAt`;
- `CreatedAt`.

Возможные состояния:

- `Unknown`;
- `Online`;
- `Offline`.

Agent считается недоступным, если heartbeat не поступал дольше настроенного порога.

### ServerInstance

Представляет управляемый серверный процесс.

Основные поля:

- `Id`;
- `AgentId`;
- `Name`;
- `Type`;
- `ExecutablePath`;
- `Arguments`;
- `WorkingDirectory`;
- `ProcessName`;
- `LogsDirectory`;
- `BackupDirectory`;
- `Status`;
- `LastProcessId`;
- `CreatedAt`;
- `UpdatedAt`.

Конфигурация должна быть привязана к конкретному Agent.

Пользователь не должен иметь доступ к `ServerInstance`, принадлежащим чужому Agent.

### ServerCommand

Представляет команду, предназначенную для выполнения Agent.

Основные поля:

- `Id`;
- `AgentId`;
- `ServerInstanceId`;
- `Type`;
- `Status`;
- `CreatedAt`;
- `ClaimedAt`;
- `StartedAt`;
- `CompletedAt`;
- `ErrorCode`;
- `ErrorMessage`;
- `AttemptCount`;
- `CorrelationId`.

Возможные состояния:

- `Pending`;
- `Claimed`;
- `Running`;
- `Completed`;
- `Failed`;
- `Cancelled`;
- `TimedOut`.

Основной переход:

```text
Pending
→ Claimed
→ Running
→ Completed
```

При ошибке:

```text
Pending
→ Claimed
→ Running
→ Failed
```

Получение следующей команды должно быть атомарным.

Одна команда не должна одновременно выдаваться нескольким экземплярам Agent.

### ServerEvent

Представляет значимое событие, произошедшее с сервером или Agent.

Примеры:

- сервер запущен;
- сервер остановлен;
- сервер аварийно завершился;
- Agent подключился;
- Agent отключился;
- команда завершилась;
- команда завершилась ошибкой.

### ServerMetric

Представляет измерение состояния процесса.

Возможные данные:

- CPU;
- используемая память;
- uptime;
- количество потоков;
- время измерения.

Долгосрочное хранение каждой метрики в PostgreSQL не является обязательным решением.

На этапе мониторинга необходимо отдельно определить, какие данные хранятся в PostgreSQL, а какие передаются в Prometheus.

### Backup

Представляет резервную копию сервера.

Основные поля:

- `Id`;
- `ServerInstanceId`;
- `Status`;
- `StoragePath`;
- `Size`;
- `Checksum`;
- `CreatedAt`;
- `CompletedAt`;
- `ErrorCode`;
- `ErrorMessage`.

### Schedule

Представляет автоматическое действие.

Примеры:

- ежедневный backup;
- перезапуск каждые 12 часов;
- backup перед перезапуском;
- удаление старых резервных копий;
- автоматический запуск после падения.

### ConfigurationVersion

Представляет сохранённую версию конфигурации сервера.

Может использоваться для:

- истории изменений;
- сравнения конфигураций;
- восстановления предыдущей версии;
- аудита.

Эта сущность не входит в текущий MVP.

## Состояния сервера

Возможные состояния:

- `Unknown`;
- `Starting`;
- `Running`;
- `Stopping`;
- `Stopped`;
- `Restarting`;
- `Crashed`;
- `Unreachable`.

Статус должен определяться на основе фактических данных от Agent, а не только по последней отправленной команде.

Например, успешное создание команды `StartServer` ещё не означает, что процесс действительно запустился.

## Идемпотентность

Система не должна рассчитывать на доставку команды ровно один раз.

Повторная обработка не должна приводить к опасному повторению операции.

### StartServer

Если процесс уже запущен, повторная команда не должна запускать второй экземпляр.

Допустимый результат:

```text
Completed: server is already running
```

### StopServer

Если процесс уже остановлен, повторная команда должна завершаться успешно.

Допустимый результат:

```text
Completed: server is already stopped
```

### CreateBackup

Повторная доставка команды не должна создавать неконтролируемое количество одинаковых резервных копий.

Для операции должна использоваться стратегия идентификации и повторной обработки.

## Мониторинг и наблюдаемость

После реализации базового функционала в проект должна быть добавлена наблюдаемость:

- структурированные логи;
- метрики;
- распределённые трассировки.

### Логи

Логи должны содержать релевантный контекст:

- `UserId`;
- `AgentId`;
- `ServerInstanceId`;
- `CommandId`;
- `CorrelationId`;
- тип действия;
- результат;
- код ошибки.

Логи не должны содержать:

- пароли;
- installation token;
- access token;
- authorization headers;
- секретные ключи.

Для централизованного хранения логов планируется Loki.

Просмотр выполняется через Grafana.

### Метрики

Примеры метрик:

- количество доступных агентов;
- количество работающих серверов;
- CPU серверного процесса;
- используемая память;
- количество созданных команд;
- количество неудачных команд;
- длительность выполнения команд;
- количество аварийных завершений;
- размер резервных копий;
- длительность создания backup;
- длина очереди RabbitMQ;
- количество повторных попыток.

Prometheus собирает метрики.

Grafana используется для дашбордов и визуализации.

### Трассировки

OpenTelemetry должен связывать один пользовательский запрос со всей цепочкой обработки.

Целевая цепочка:

```text
React
→ ASP.NET Core API
→ RabbitMQ
→ Windows Agent
→ выполнение команды
→ результат
→ ASP.NET Core API
```

На этапе HTTP polling трассировка может охватывать отдельные запросы и коррелироваться через `CorrelationId`.

## Безопасность

Windows Agent управляет процессами и файлами, поэтому безопасность является обязательной частью проекта.

Основные требования:

- пользователь и Agent используют разные механизмы аутентификации;
- регистрация Agent выполняется по одноразовому ограниченному по времени токену;
- в базе хранится hash installation token;
- credentials Agent можно отозвать;
- каждая команда адресована конкретному Agent;
- Agent получает только собственные команды;
- пользователь может управлять только своими агентами;
- пользователь может управлять только серверами собственных агентов;
- Agent не выполняет произвольные PowerShell-команды;
- Agent не выполняет произвольный shell-код;
- Agent поддерживает только известные типы команд;
- пути к файлам должны проверяться;
- необходимо учитывать path traversal;
- секреты не хранятся в исходном коде;
- production-соединение использует HTTPS;
- чувствительные настройки передаются через environment variables или безопасное хранилище;
- действия пользователей и агентов должны записываться в аудит;
- ошибки не должны раскрывать внутренние секреты;
- повторная доставка сообщения не должна повторно запускать опасную операцию.

## Резервное копирование

Резервное копирование не входит в текущий MVP.

Целевой процесс:

1. Backend создаёт команду `CreateBackup`.
2. Agent получает команду.
3. Agent проверяет состояние сервера.
4. При необходимости сервер корректно останавливается.
5. Нужные файлы архивируются.
6. Рассчитывается checksum.
7. Архив сохраняется локально или загружается в объектное хранилище.
8. Agent сообщает результат backend.
9. При необходимости сервер запускается обратно.

Необходимо учитывать:

- нехватку места на диске;
- невозможность чтения файлов;
- отмену операции;
- падение Agent во время создания backup;
- повторную доставку команды;
- повреждённый архив;
- ограничение количества хранимых копий;
- восстановление после частичной ошибки;
- проверку архива перед восстановлением;
- запрет восстановления во время работы сервера.

## Текущий MVP

Актуальное описание текущего MVP находится в `docs/mvp.md`.

В него входит минимальный вертикальный сценарий:

```text
Пользователь
→ ASP.NET Core API
→ PostgreSQL
→ HTTP polling
→ Windows Agent
→ локальный процесс
→ результат выполнения
→ API
```

Основные функции текущего MVP:

- регистрация пользователя;
- авторизация;
- создание installation token;
- регистрация Agent;
- heartbeat;
- создание `ServerInstance`;
- создание команды `StartServer`;
- создание команды `StopServer`;
- получение команды через HTTP polling;
- запуск тестового локального процесса;
- остановка процесса;
- отправка результата;
- история команд;
- базовые unit-тесты;
- интеграционные тесты с PostgreSQL;
- Docker Compose для API и PostgreSQL.

В текущий MVP не входят:

- React;
- RabbitMQ;
- Redis;
- Kubernetes;
- Grafana;
- Prometheus;
- Loki;
- MinIO;
- резервные копии;
- расписания;
- уведомления;
- управление произвольными командами ОС.

## Целевая первая полноценная версия

После завершения текущего MVP проект должен постепенно получить:

- React-интерфейс;
- поддержку Project Zomboid;
- отображение CPU и RAM;
- просмотр последних логов;
- создание локальных резервных копий;
- обработку ошибок;
- базовый CI через GitHub Actions;
- Docker Compose для серверной части;
- рабочий деплой на VPS.

Это не текущий MVP.

Функциональность добавляется отдельными этапами и небольшими проверяемыми задачами.

## Архитектурные ограничения

Проект не должен преждевременно превращаться в набор микросервисов.

Для целевой архитектуры достаточно:

- одного ASP.NET Core API;
- одного Worker Service;
- одного Windows Agent;
- одного React-приложения;
- PostgreSQL;
- RabbitMQ после завершения базового сценария.

Разделение на дополнительные сервисы должно происходить только при наличии конкретной причины.

Необходимо избегать:

- преждевременных универсальных абстракций;
- сложной Clean Architecture ради самой архитектуры;
- generic repository поверх EF Core;
- добавления технологий для количества;
- сущностей и интерфейсов под гипотетические будущие требования;
- произвольного выполнения команд ОС;
- хранения секретов в репозитории;
- попытки внедрить всю инфраструктуру одновременно.

Kubernetes, Redis, MinIO, RabbitMQ и сложный мониторинг не должны внедряться до появления рабочего основного функционала.

## Критерий успешности проекта

Проект можно считать успешным, если пользователь способен:

1. установить Windows Agent;
2. зарегистрировать его в системе;
3. добавить локальный сервер;
4. удалённо запустить сервер;
5. удалённо остановить сервер;
6. увидеть актуальное состояние;
7. посмотреть нагрузку;
8. посмотреть логи;
9. создать резервную копию;
10. восстановить резервную копию;
11. увидеть историю действий;
12. получить понятную информацию при ошибке;
13. настроить автоматические действия;
14. развернуть серверную часть через CI/CD;
15. наблюдать состояние системы через Grafana.

Главная ценность проекта — не количество функций, а качественная реализация взаимодействия между веб-приложением, backend, PostgreSQL, брокером сообщений и Windows Agent.
